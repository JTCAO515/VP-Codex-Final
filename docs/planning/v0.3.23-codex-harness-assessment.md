## 0. 结论先行

| 问题 | 结论 |
|---|---|
| Codex harness 开源后能否加入 VisePanda 开发? | **它早就在了**——Codex 是本项目的 iOS 工程师(`WORKFLOW.md`)。真正的问题不是"要不要用 Codex",而是"harness 开源能不能让现在靠人工传话的部分自动化"。 |

但要加一句本项目特有的:

> **本项目已经是三 Agent 协作;harness 的价值不在"引入 AI",而在"给已有的三个 AI

## 2. Codex Harness 开源了什么(已核实部分)

官方把 harness 定义为模型之外的 Agent 执行系统:收集上下文、维持会话、调用工具、
流式输出进度、处理失败、请求审批、跨轮次继续。开源的组件:

| 组件 | 许可 | 用途 | 对本项目的判断 |
|---|---|---|---|
| Codex CLI | Apache-2.0 | 终端 coding agent | 已在用(Codex 是 iOS 工程师) |
| `codex exec`(非交互) | Apache-2.0 | 脚本、CI、一次性任务 | **本轮推荐的唯一入口** |
| Codex SDK(TS/Python) | Apache-2.0 | 代码里启动/续接 thread | 第二阶段可选 |
| app-server | Apache-2.0 | 产品内深度集成、历史、审批、事件流 | **不适合本项目**(见下) |
| `openai/codex-action` | Apache-2.0 | GitHub Actions 集成 | 需 API key,暂缓 |

**app-server 为什么不适合本项目**:除了 WebSocket 传输官方明标实验性/不支持生产
之外,更根本的是本项目的 Web 端跑在 Vercel serverless 上——没有常驻进程可以承载
app-server 的长连接与本地执行环境。这一点 GPT 报告说对了。

`openai/codex-action` 的两个已核实细节值得记下:
- 它自带 `permission-profile` 和 `safety-strategy`(默认 `drop-sudo`)输入参数,
  说明官方本身就把权限收敛当成一等公民;
- 官方 README 的示例里,反馈类任务是**给了** `issues: write` / `pull-requests: write`
  的。GPT 报告主张"模型 job 绝不持有写权限"——那是一条**更严格的项目自定策略**,
  不是官方硬性要求。我倾向于采纳 GPT 的严格版,但要注明这是我们的选择而非官方约束。

## 3. 本项目真实现状(GPT 报告完全没有覆盖的部分)

这是重写的根本原因。截至 `main@1aa2cbb` / `v0.3.22`:

### 3.1 已经是三 Agent 协作(`WORKFLOW.md`)

| 角色 | 职责 | 泳道 |
|---|---|---|
| **Claude Code** | 架构师 / Reviewer / **唯一合并权** / 维护全部共享文档 / dev→main 发布 | 调度台 |
| **Antigravity** | `android/` 全部开发 | Android 泳道 |
| **Codex** | `ios/` 全部开发 | iOS 泳道 |

操作者是**人肉消息总线**,每轮复制粘贴三句固定话术(【派活】/【审核】/【转驳回】)。

→ **所以"Codex 能不能加入 VisePanda 开发"这个问题的前提已经不成立了:它已经是
核心开发者之一。** GPT 报告把 Codex 当成一个待评估的新工具来论证,这个框架本身
就过时了。

### 3.2 代码现状

```
app/ components/ lib/ tests/     Web(Next.js,已上生产,真实 LLM 已接通)
android/                          Android 原生(Kotlin/Compose,功能已较完整)
ios/                              iOS 原生(SwiftUI,VisePandaIOS.xcodeproj)
supabase/ docs/ scripts/
```

### 3.3 CI 现状(核实结果)

| 泳道 | CI | 内容 |
|---|---|---|
| Web | ✅ `.github/workflows/web-ci.yml` | ubuntu,node,测试+构建 |
| Android | ✅ `.github/workflows/android-ci.yml` | ubuntu,`:app:testDebugUnitTest :app:assembleDebug` |
| **iOS** | ❌ **没有** | `WORKFLOW.md` 原话:"**iOS 无 CI,截图是硬要求**" |

### 3.4 同一契约的三份实现(本项目最特别的结构性风险)

| 契约 | Web | Android | iOS |
|---|---|---|---|
| 行程模型 | `lib/types/trip.ts` | `data/model/TripModels.kt` | `Models/TripModels.swift` |
| 完成度算法 | `lib/trips/completeness.ts` | `data/model/TripCompleteness.kt` | (待核) |
| Butler/对话 | `lib/types/trip.ts` 内 | `ButlerModels.kt` | `ButlerModels.swift` |
| 翻译 | `lib/...` | `TranslateModels.kt` | `TranslateModels.swift` |
| 探索 | `lib/explore/...` | `ToolsModels.kt` 等 | `ExploreModels.swift` |
| 认证 | `lib/supabase/...` | `AuthModels.kt` | `AuthModels.swift` |

`DESIGN.md` ADR-094 已经规定 Web↔Android 必须**行为一致**(连四舍五入都对齐),
但:

- **没有任何自动化在检查这条规定**;
- iOS 是后来加的,**没有等价的 ADR**,也没有被 ADR-094 覆盖;
- 三份实现由**三个不同的 AI**分别维护,分别提 PR。

这就是本项目最适合上 AI 检查的地方,详见 4.2。

## 4. 三个真实痛点与优先级

### 4.1 【P0】iOS 没有 CI —— 而且**最佳解法不是 Codex harness**

这是本次核查发现的最大且最具体的漏洞。当前 iOS 的质量保证链条是:

```
Codex 自己写代码 → Codex 自己构建 → Codex 自己跑模拟器 → Codex 自己截图 →
Codex 自己填 PR 模板说"通过了" → 人类看截图 → 合并
```

**全链条没有一个独立于实现者的验证环节。** GPT 报告花了很大篇幅担心"PR 描述说
已通过但真实 check-runs 未结束"这类"假绿"风险——在本项目里,iOS 泳道**根本没有
check-runs 可以查**,这个风险不是假设,是现状。

而且 `WORKFLOW.md` 记录了一个真实事故:Issue #28 因为 PR #30 CI 红灯,操作者
决定换人接手(Antigravity → Codex)。协调摩擦是真实成本。

**关键判断(与 GPT 报告方法论的最大分歧):**

> 这个 P0 漏洞的正确解法是**在 GitHub Actions 的 macOS runner 上跑 `xcodebuild`
> 做确定性构建 + 单元测试**,而**不是**上一层 AI 检查。

理由:一个 AI preflight 只能说"我读了 diff,看起来没问题";而 `xcodebuild` 能给出
"编译通过/失败"这个不可辩驳的事实。**在有确定性手段可用的地方引入 AI 判断,是把
可证伪的事实降级成概率意见。** GPT 报告的框架会引导你去建 AI preflight,却没意识到
这个项目缺的是最基础的编译验证。

`ios/VisePandaIOSTests` 已经存在,说明测试目标是有的,接 CI 的成本不高。

**建议动作(不需要任何 AI、不需要任何 key):**
```
.github/workflows/ios-ci.yml
  runs-on: macos-latest
  paths: ["ios/**"]
  → xcodebuild build-for-testing / test -scheme VisePandaIOS
     -destination 'platform=iOS Simulator,name=iPhone 15'
```
注意:macOS runner 计费远高于 ubuntu,需要用 `paths:` 严格限定只在 `ios/**` 变更时
触发,并考虑并发取消。这是操作者需要知道的成本影响。

### 4.2 【P1】跨语言契约漂移 —— **这才是 Codex harness 的真正落点**

三份实现、三个 AI、零自动检查(见 3.4)。会出现的具体故障:

- Android 加了 `TripBlock.crowdRisk`,iOS 没加 → 同一行程两端显示不同;
- Web 的 completeness 改成七维,Android 还是六维 → 同一份行程两端 readiness 百分比
  不同(ADR-094 明确要防的就是这个);
- iOS 把 `BookingCandidate.status` 的 `InfoOnly` 渲染成可点击预订 → 触碰
  "不暗示交易能力"的产品红线。

**为什么确定性 CI 做不了这件事**:你没法用 linter 把 Kotlin data class 和 Swift
struct 和 TypeScript interface 三向 diff。字段名会有大小写/命名习惯差异
(`chineseAddress` vs `chinese_address`),可选性表达方式不同,枚举写法不同。
这是**语义比对**,不是文本比对。

**为什么这正好是受约束 AI 的强项**:输入是三个文件的内容(公开代码,无密钥、
无用户数据),输出是结构化的"字段级差异列表",只读、无副作用、可 schema 校验。

**建议形态**(参数名待本地核对):
```
scripts/contract-drift/collect.mjs      # 确定性抽取三份契约文件
  → codex exec 只读 + JSON schema 输出
  → { drifts: [{ field, presentIn: [...], missingIn: [...], severity }] }
  → 仅作为 PR 评论的建议,不阻断合并(先观察准确率)
```

先在本地手动跑,验证它能不能在已知的历史漂移上给出正确答案,再考虑进 CI。

### 4.3 【P2】操作者的人肉传话负担

三句固定话术、双泳道、每轮手动触发【审核】。harness 理论上能自动化这个 relay,
但**我不建议现在做**:

- 自动化 relay 意味着让 AI 决定"什么时候该派活/该审核",这是把调度权从人手里拿走;
- 当前工作流刚跑通、且已经出现过换人接手的情况,人在环路里是有价值的;
- 收益(省几次复制粘贴)远小于风险(失控的自动合并链)。

→ **明确建议:暂不自动化。** 等 P0/P1 稳定运行一段时间后再评估。

## 5. 推荐方案

### 5.1 分层结论

| 层次 | 是否用 Codex Harness | 与 GPT 报告的异同 |
|---|---|---|
| iOS 构建验证 | **否——用确定性 `xcodebuild` CI** | **GPT 报告没有覆盖此项**,这是最大补充 |
| 跨语言契约漂移检查 | **是,只读 + 结构化输出** | GPT 报告没有此项(它的仓库没有三端) |
| PR preflight / review | 可选,优先级低于上两项 | GPT 报告的 CH-04/CH-05/CH-07,方向对但本项目已有 Claude Code 做 reviewer,增量有限 |
| 操作者 relay 自动化 | **暂不做** | GPT 报告未涉及 |
| 游客产品(Chatbot / Trip) | **绝不** | 与 GPT 报告完全一致 |

### 5.2 为什么 PR review 的优先级被我下调

GPT 报告把 preflight/review 当成第一优先(CH-03…CH-07)。在**它描述的那个仓库**里
这可能对——那里 Claude Code 似乎不是固定 reviewer。但**在本仓库**,`WORKFLOW.md`
已经把 Claude Code 定为架构师 + Reviewer + 唯一合并权,每轮【审核】会执行
"CI 状态检查 → Scope 越界核对 → 五条硬规则审核"。

再叠一层 Codex preflight,收益是"多一个模型的意见",成本是多一份 token、多一套
脚本、多一处可能与 reviewer 结论冲突时的仲裁负担。**在 iOS 连编译验证都没有的
情况下,先补那个洞的边际收益高得多。**

### 5.3 游客产品:借模式,不接 harness(与 GPT 报告一致)

我完全认同 GPT 报告第 6 节的判断和它的 Relay 模式映射。补充一条本项目现状:
`v0.3.19` 已经明确**移除了 Chat 的 mock fallback,改为诚实的连接失败状态**
(ADR-120),`v0.3.17` 建了 provider 熔断器。这条窄管道正在正确的方向上加固,
不应该被一个通用 coding agent harness 替换。

harness 值得借鉴到产品里的**唯一**思想是:
> 界面掌握业务记录 → Agent 调查并提议 → **有后果的动作等待用户确认** → 确定性服务执行写入。

这和现有 `CanvasPatch` 管道的设计意图一致,不需要引入新依赖。

## 8. 操作者需要知道的

### 现在不需要你做任何事

P0(iOS CI)和 P1 本地验证都不需要新账号、新 key 或新配置。

### 未来可能需要你做的

1. **macOS runner 成本**:GitHub Actions 的 macOS runner 计费倍率显著高于 ubuntu。
   接 iOS CI 前你需要知道这会消耗多少额度,以及是否要限制触发条件。
2. **OpenAI API key**(仅当契约检查要进 CI 时):`openai/codex-action` 只接受
   API key,**你现有的 ChatGPT/Codex 订阅不能用于 GitHub Action**——这一点已核实。
3. **不要把 `~/.codex/auth.json` 上传到任何地方**。官方将其视同密码。

### 需要你澄清的一件事

GPT 报告描述的 `VP-Final` 仓库(monorepo、Ops 后台、Content AI、引用体系、
OA Register)——**这是另一个真实存在的项目,还是那份报告的推断?**
这直接决定那份报告的第 3/4/5/7 节是否还有执行价值。
